# Optimus — Project Rules (read before every task)

## What this project is

German-language health-tech web app ("Optimus"). Next.js App Router + TypeScript (strict) + Tailwind CSS v4 + shadcn/ui. All user-facing text is German. Current build scope: site shell, then Dashboard (`/dashboard`) and Analysis (`/analyse`) only — all other pages stay stubs until explicitly requested.

## Architecture rules (do not violate)

- Route groups: `app/(marketing)` = public pages, `app/(app)` = logged-in area, `app/(auth)` = login/register. Route files stay THIN — they only compose; real UI and logic live in `features/<domain>/` (components/, hooks/, index.ts).
- The context rail is filled BY THE ROUTE, through the parallel slot `app/(app)/@rail`. The layout knows the place, not the content: it takes the slot as a `rail` prop and puts it in two spots, the column above `xl` and the drawer below it. `@rail/[...alleAnderen]` serves the normal composition to every route, and `@rail/<route>` overrides it for one — today only `/empfehlungen`. **That catch-all is not optional**: without it a parallel slot keeps its last active sub-path on soft navigation, so the reduced rail would follow you onto the dashboard. `@rail/default.tsx` is the same thing for a hard load, and Next refuses to build a slot without it — the two are a pair and must show the same thing. Compose a new rail out of the tiles `context-rail.tsx` exports (`RailTile`, `ProfileTile`, `OpenQuestionsTile`); building a second set of tiles is how the rail starts drifting apart page by page.
- A slot is not a route segment and never appears in the URL. `LayoutProps` learns the prop from the folder, which means `next typegen` (or `next dev`/`next build`) has to run once after adding one.
- Domain data flows through `contracts/` (TypeScript interfaces + Zod schemas) → repository implementations in `data/mock/` (later `data/http/`). Components NEVER fetch directly or know which implementation is active. Reads go through TanStack Query hooks in the feature folder.
- That layer is HALF BUILT. `contracts/` holds biomarkers and supplements; `data/mock/` holds the supplements and is a synchronous export, not a Promise-based repository, and TanStack Query is not installed yet. The remaining domains (dashboard markers, context rail) still keep their mock data in `features/<domain>/sample-data.ts` and are imported directly by routes. Two places for the same kind of thing is a transitional state, not the pattern: whoever touches one of those domains next brings it along. A type belongs in `contracts/` once a SECOND surface needs it — that is what moved `Supplement` out of `features/analysis`.
- Shared primitives: `components/ui/` (shadcn, owned). App-wide composed components: `components/common/`. Helpers: `lib/`.
- Never delete or rename existing routes/folders without being asked.

## Design system (single source of truth)

- `tokens/tokens.json` (W3C DTCG format) is the ONLY source for colors, spacing, radii, typography, shadows, blur. Styling goes through the CSS variables / Tailwind theme derived from it (see `app/globals.css`).
- FORBIDDEN in components: raw hex/rgb/hsl values, arbitrary Tailwind values like `w-[437px]` or `bg-[#A32432]`, inline style colors. If a needed value is missing, ADD a token first, then use it.
- Brand palette: crimson — Tint #EBC0C5, Light #C96773, Base #A32432, Dark #6E1822 (already tokenized; never re-hardcode these).
- Red is an ACCENT color only (primary buttons, active states, highlighted values, chart accent) — never large surfaces. Headings are neutral-dark.
- The Dashboard marker cards DO interpret: the trend line takes a status colour from where the current value sits (green in target / amber borderline / red outside the reference range) and the change pill takes one from whether the last move went toward or away from that target. Both readings come from `features/dashboard/rules.ts` — the only place the dashboard is allowed to form a verdict — and both must survive greyscale: the reference track under the curve carries the same standing as a POSITION, and the change pill spells its verdict out in a word ("günstig" / "ungünstig"). Everything else on the dashboard stays greyscale plus the brand accent, and the decorative category chips must stay clear of green/amber/red so a tint never reads as a verdict.
- Status colours carry verdicts on the Analysis surface, including `/analyse/snapshot`. There the whole page speaks ONE scale — gut / grenzwertig / kritisch, thresholds in `features/analysis/rules.ts` (`toScoreVerdict`, ⚠️ placeholder), appearance in `features/analysis/components/score-verdict.tsx` — and it reuses the existing success/warning/critical tokens rather than adding any. Read the colour policy block in `features/analysis/components/analysis-board.tsx` before putting colour anywhere on that page: grey is the default state, at most one coloured element per row, and a filled pill marks anything that comes from one of the three scales — verdict (`VerdictChip`), movement (`ScoreDelta`) or supplement status. Everything else stays text: the priority findings carry a mark and a figure, and decorative category icons (`CategoryIcon`) are neutral-toned wherever they appear. No status colour in the Entwicklung chart itself (the deltas beside the lines carry it, the field never does) or on the dark score tile, and thin Datenlage never carries a verdict. The Ansatzpunkt rank discs are graphite, not brand red, so red keeps a single meaning.
- `/empfehlungen` deliberately carries NO status colour at all. Green, amber and red answer exactly one question in this product — where a measured value stands — and that question belongs to the dashboard and the analysis. The recommendation page answers two different ones: how strongly something is recommended, and whether it is in the subscription. Colouring a recommendation strength would make it look like a finding: "Optional" in amber reads as a warning and means the opposite, namely that we can judge nothing at all. TWO things on that page are coloured, both actions, both inside the cart: "Änderungen übernehmen" in brand red (`railPrimary`) and the cancellation warning in the danger tokens with an icon and a word (`railDestructive` / `criticalOnRail`, because that surface has its own token family). That is the whole list, and it is short on purpose — brand red is the one thing on this page that means "press me", so nothing that merely IS may wear it. Three things used to and no longer do: the tint on a newly joining row (a `bg-brand-subtle` fill, which made the largest area of the page the same colour as its most important button), the "neu" badge (now a grey mark with a `+` and the word), and the row switches (a column of filled brand-red tracks reads as eight actions when it shows a state — they are graphite now, in `components/ui/switch.tsx`, and that is the primitive's default everywhere). `BiomarkerBar` is where the rule is hardest and must hold: it shows precisely what the dashboard WOULD colour — where a value stands against its target — and it stays greyscale (`--color-track-base` for the axis, `--color-track-reference` for the target segment). What carries the reading is SHAPE plus words: the dot is filled inside the target range and an open ring before it, from the same `isInTarget` test that writes the sentence underneath, so the two can never contradict each other. They did: Ferritin 68 against a target from 70 said "noch unter dem Zielbereich" while the dot appeared to sit inside the segment, because two units of axis are narrower than the dot itself. Read the colour policy block in `features/empfehlungen/components/recommendation-board.tsx` before putting colour anywhere on it.
- The LEFT COLUMN of `/empfehlungen` carries no monetary amount at all — not in a row, not in the header, not on a discontinued item, not as a small grey per-month price. The list answers "what do I have, what changes, why"; money answers none of those, and a row with a price on it reads as an offer rather than a finding. Amounts, the before/after balance and the confirmation live in the cart, which is the page's ONE commercial surface. A `StackSummaryBar` under the list used to repeat the balance and carry a second confirm button; it is gone, and bringing it back means bringing back both the checkout in the middle of the evaluation and two "Änderungen übernehmen" in one document. ⚠️ Known consequence, not an oversight: below `xl` the cart exists only in the rail drawer, so while that drawer is shut the page shows no total and offers no confirmation — the way there is the `PanelRight` button in `app-shell-header.tsx`. A test asserts the rendered board contains no `€`.
- The target range a `BiomarkerBar` draws comes from the DATA (`targetRange` on `Supplement`, `contracts/supplement.ts`), never from the component. A reference range typed into a bar is a medical claim in a layout file, and it would then differ from the same marker on the dashboard. The schema keeps `targetMarker` and `targetRange` bound to each other — both null or both set — so a supplement cannot name a marker it has no range for and end up with a bar scaled against nothing. ⚠️ In `data/mock/supplements.ts` only three ranges are real (they are copied from the corresponding marker's `optimalLow`/`optimalHigh`); the ranges for Magnesium, Zink and Holo-Transcobalamin are INVENTED, marked as such at each entry, and must be replaced before anything ships.
- Recommendation strength and subscription membership are TWO AXES and must never merge. Strength (`empfohlen` / `optional` / `nicht mehr empfohlen`, derived in `features/empfehlungen/rules.ts`) is the page's structure; membership is a property of the single row, so the same membership can appear in any section. A section called "weiter nehmen" would be exactly the merge — the test is the first visit with an empty subscription: the structure must be identical, only `nicht mehr empfohlen` falls away, because nothing can be discontinued that is not running. There is a test for it in `test/empfehlungen.test.tsx`. The three headings NAME THE REASON, not the verdict — "Basierend auf deinen Blutwerten", "Optionale Ergänzungen", "Fällt weg" — because they took over the job of the per-row status badges: once the heading says why the rows below it are there, every row can drop the badge and the section becomes readable in one line instead of eight. They carry no COUNT beside them either; the digit counted what stood directly underneath it and shared a line with the section's point. A heading must never come to mean "what you take" — the first section is the proposal from the evaluation, membership is read from the switch positions and the cart, and the empty-subscription test is the proof: full stack, empty subscription. The "im Abo" mark that used to sit on the row is gone: it described the normal case and was therefore the page's most frequent badge, while the two marks worth seeing are the CHANGES ("neu", "wird entfernt").
- The cart on `/empfehlungen` lives IN THE CONTEXT RAIL and nowhere else — the column from `xl` up, the drawer below it. It is rendered from `RecommendationBoard` through `createPortal` into the node `RailCartSlot` registers, so the pending changes stay ordinary props instead of moving into a global store just so two neighbours in the same picture can agree. The board asks ONE question: is there a visible node in the rail? If there is not, there is no cart — see the left-column rule above for why there is no longer a fallback bar under the list. The two-step cancellation prompt lives in the board rather than in the cart, so resizing or opening the drawer mid-prompt does not restart it.
- A rail tile that must EXIST rather than merely look different per placement reads `useRailPlacement()` (`components/common/rail-placement.tsx`). The column is in the DOM below `xl` but `display:none`, so registering a portal target there would put the cart — the only place with amounts and a confirmation — behind a `display:none` while the page believed it was housed; the drawer only exists while open, where present equals visible. `RailCartSlot` keeps a STACK of nodes, not one slot: the last registration wins (always the drawer, which arrives later and leaves earlier) and closing it falls back to the previous node instead of to nothing.
- `lib/use-media-query.ts` is the ONLY breakpoint in JavaScript and stays that way. Everything that merely LOOKS different at a width uses Tailwind or a container query — CSS knows the width before first paint, JavaScript only after hydration. The hook exists for the one thing CSS cannot do: decide WHERE in the tree an element is created, as with the cart's two possible parents. Rendering both and hiding one is the CSS answer and would put two confirm buttons in the document.
- The cart opens PRE-FILLED with the proposal from the last evaluation (`toRecommendedChanges`), but only with what the evaluation can actually stand behind: everything `empfohlen` goes in, everything `nichtMehrEmpfohlen` is carried out, and `optional` is left alone. That last line is the answer to the question this rule used to leave open — `optional` means "we can judge nothing here", and a cart that pre-selects it sells on a shrug. Optional supplements are therefore OPT-IN, and the cart's total starts at the core stack. The page still asks "do you accept this?" rather than "assemble one" — with eight rows the second is a chore, not a decision — and that convenience is its most dangerous spot, so three conditions are non-negotiable and a test guards each: nothing happens without confirmation (the proposal is a pending change like any other), every row can be flipped back, and the cart says in words that it is a proposal and where it came from. A pre-filled cart that fails any of the three is a cart somebody slipped you.
- Because of that pre-fill, a row has exactly ONE control and no third state: a `Switch` whose checked state IS "in the next subscription". It used to be a pair of "Hinzufügen" / "Entfernen" buttons, and "Entfernen" was then the most repeated word on the page — the destructive one, printed eight times under a proposal the user had not even accepted yet. A switch names the state instead of the loss, and it is the same control in both directions. The difference from the running subscription stays a grey mark next to the name ("neu", "wird entfernt"), which describes a state instead of claiming a history; "Rückgängig" would be the page's most common label, on rows nobody touched. `toggleMembership` in `features/empfehlungen/rules.ts` owns the flip, and it deletes a pending entry rather than inverting it, so "no pending change" stays identical to "nothing to confirm".
- In the CORE STACK those switches only appear in the "Zeile für Zeile anpassen" mode; the default view is read-and-accept. Standing open, they were eight controls in the same position, which is no information at all, and they were the loudest thing on a page whose point is the measurements. This costs one click on the revert that the pre-fill is conditional on, and three things pay it back — none of them optional: the mode toggle sits NEXT TO THE FIRST HEADING (visible without scrolling, not at the foot of the list), the optional section keeps its switches whatever the mode (a control that is not there cannot be opted into, and opt-in is the whole point of that section), and the cart keeps calling its proposal a proposal. Hide the toggle, move it below the list, or take the switches off the optional rows, and the pre-fill loses its justification.
- No efficacy claims anywhere on `/empfehlungen` — not "wirkt", not "hilft gegen", not "unterstützt". Every row justifies itself with measurements ("25-OH-Vitamin-D 17 → 44 ng/ml") and, where there are none, with a SHORT EXPLANATION in whole words — never with the name of one of our fields. "kein messbarer Zielmarker" was exactly that mistake: it reads as an error message to anyone who does not know the term and as the evaluation talking about itself to anyone who does. What a row without a measurement can honestly say is where the recommendation comes from ("aus deinem Fragebogen, nicht aus einem Blutwert", from `basis` in `contracts/supplement.ts`) or when it becomes assessable ("läuft seit 28 Tagen — beurteilbar ab 04.08.2026"). The SOURCE is allowed, its TOPIC is not: "aus deinem Fragebogen: Schlaf" is the claim that the supplement acts on sleep, which is why `basis` is an enum and not free text. All five wordings live in `toEvidence`. The page closes with a grey legal note (`recommendation-board.tsx`, ⚠️ not cleared): the statutory NemV sentence, where the recommendations come from and that they carry no warranty, and who should ask first. It deliberately does NOT say that supplements "can help" — that is the unspecific health claim the whole page avoids, and a note whose job is to lower expectations must not raise one. It stays grey and iconless, because the danger tokens on this page belong to the cancellation in the cart. It is COLLAPSED by default, but the collapse keeps a visible one-line short form (`LEGAL_SHORT`) with the NemV sentence in it — the statutory part is never the part behind the click, only the full text (`LEGAL_NOTE`) is. The panel is `hiddenUntilFound`, so browser search finds the closed text.
- The product photo belongs to `DeliveryTile` on the rail, under the cart — it answers "how does this reach me", which is that tile's question, and it is the one place on this page where a photo says something rather than being recognition, so it has real `alt` text. It spent one round at the top of the content column and that was wrong: the first thing on a page whose job is an evaluation was a picture of the packaging. It must not be in both places; a second copy turns the first into decoration. ⚠️ The motif is still wrong — needed is ONE sachet, front-on, PORTRAIT; the existing asset shows stacked boxes with loose capsules. The frame is already portrait (`aspect-3/4`) and crops the old image, with a `TODO` at the tile: swapping in the right file should touch nothing but the import and the `alt` text. The 30-per-month figure and the first delivery month are placeholders like the prices. Product claims from the packaging ("vegan", "ohne künstliche Zusatzstoffe") stay in the photo and are not repeated as text — those need a clearance the project does not have, as does any statement about what a supplement does. A test asserts the rendered page contains none of those words.
- A row on `/empfehlungen` EXPANDS IN PLACE (`button` with `aria-expanded`, panel in `reason-panel.tsx`) and never navigates. The page used to show measurements plus a grey chevron on the product name, which promised a detail route that does not exist and answered nothing; the whole row is the trigger now, and the promise is redeemed where it is made. Three things make that readable and each has a reason: the interpretation sentence under the bar is CLAMPED TO ONE LINE with an ellipsis (`truncate`, not `line-clamp`, so every row keeps the same height and the bars stay on one baseline) — the cut is the invitation, and a wrapping sentence removes it; the affordance sits at the end of the row where the price used to be, as a "Begründung" span INSIDE the row button rather than a nested button; and the FIRST row starts open, because a list in which every justification is closed looks exactly like a list without justifications, which was the complaint. Several rows may be open at once — these are justifications one compares, and an accordion that closes the previous one prevents that. ⚠️ The open set is component state, like the pending changes: which supplements someone expands is health data and must not go to `localStorage` or the URL, so "persisted" here means across re-renders, not across reloads. `toReasonDetails` OMITS fields it has no data for instead of rendering them empty.
- The header of `/empfehlungen` reports the TEST, not the offer: overline "Dein Test vom …", headline "{n} von {m} Werten liegen näher am Zielbereich als im {Monat}", one sentence naming which markers are in range and how many new starting points there are. Every number is computed in `toEvaluationSummary`, and they count VALUES, not preparations — a supplement from the questionnaire has no measurement and must not appear in "n von m", and a marker without a second measurement is not "compared" either. Without any comparison (first visit) the headline falls back to "{n} Ansatzpunkte in deinen Werten gefunden". The headline is worded that way because "haben sich verbessert", the obvious phrasing, is the one line on this page that comes near an efficacy claim: over a list of preparations it reads as their doing. ⚠️ That is DEFERRED, not rejected — it needs sign-off, and if it arrives, exactly this one line changes. What stands there now is literally what is computed: `closer` counts the values whose DISTANCE to the target range shrank (`toTargetDistance`), which is not the same as "moved in the expected direction" — a value that overshot its range moved the right way and is further from the range than before. In a ROW, next to a product name, "verbessert" would claim that THIS preparation moved the value, and that stays banned whatever the header is allowed to say; a test forbids it inside every `li` and, while the sign-off is missing, on the whole page.
- Look: glassmorphism, built as three surface levels over a fixed mesh-gradient backdrop plus a 3% grain overlay. The `(app)` shell uses `.glass-shell` (floating panel) and `.glass-rail` (detached icon rail), `.surface-content` for the content area, `.surface-card` for the SOLID cards on it, and `.rail-card` for the context rail's tiles. From `xl` up the rail has NO surface of its own: the tiles sit directly on the mesh backdrop. It used to be a second glass panel, and that was the mistake — two pale glass surfaces a 16px gap apart read as one split surface rather than two columns, because the gap is too narrow to separate and the surfaces too alike to do it themselves. The backdrop does separate. Because those tiles now stand on bare ground, `.rail-card` carries the deeper `--shadow-lift` where `.surface-card` carries `--shadow-card`; that second shadow replaces the lift the panel used to give them and is not a new effect. `.rail-panel` stays alive for exactly one caller, the below-`xl` drawer in `components/ui/sheet.tsx` — there the rail floats OVER the content and does need a surface. Do not put it back on the `xl` column. Glass surfaces are never opaque — the backdrop must show through. The older `.glass` / `.glass-strong` / `.glass-subtle` utilities remain for marketing pages. Keep the `@supports not (backdrop-filter…)` opaque fallback intact.
- Pages inside `(app)` carry NO visible page heading — no eyebrow, no big `h1`, no lead paragraph. The navigation already says where you are and the tab title repeats it; a 36px line plus its spacing cost the first ~90px of every screen to say it a third time. The `h1` stays in the markup as `sr-only`, because a page without one is a page without a name for anyone navigating by headings. Every page follows this, and a new page joins them rather than reintroducing the pattern for itself. `EvaluationHeader` on `/empfehlungen` is not an exception to it: the `h1` there is `sr-only` like everywhere else, and what stands at the top is not the page's NAME but its RESULT — which test, how many values moved, which are in range. That is the line the rule is protecting the space for. A header that read "Deine Empfehlungen" over the same list would be exactly the banned heading with a date above it. The content column's top inset is `xl:pt-5` to match the rail's `py-5`, so the first card in each column shares one top edge; change one and change the other.
- On the context rail use only the on-rail token family (`text-on-rail*`, `border-rail-line*`, `*-on-rail` status colours, `ring-on-rail`) and the `rail*` button variants. They currently match the content-surface roles, but staying inside the family is what lets the rail change its surface without touching every component on it — which it has now done once, losing its panel above `xl` without costing a line in `context-rail.tsx`. The rail runs a FOUR-STEP type scale — 16px for the panel name and the profile name, `panel-title` for every tile heading (the same chain the content cards use), 12px for prose, 11px for labels and timestamps — plus one value outside it, the 18px test date. Adding a fifth step, or reaching for the buttons' default `sm` size (12.8px, between two real steps), is what made it look unmatched before. Exactly ONE thing on the rail is brand red PER PAGE — on most pages the next test, shown twice in the same tile as the countdown and the planned timeline dot; on `/empfehlungen`, where that tile is not in the composition, the "Änderungen übernehmen" button in the cart (`railPrimary`) — which is also the only brand red on that whole page, left column included. Adding a second one is what turns brand red from a pointer into decoration, so a rail that wants a red action drops the red tile, not the other way round. Open questions never take colour — the rail is barred from every verdict, and red on an unanswered question would be one.
- Error/danger UI uses the orange-red danger tokens (NOT brand red) and always pairs color with an icon or text label.
- Font: IBM Plex Sans via `next/font/google` (self-hosted at build). NEVER add Google Fonts `<link>` tags (GDPR).
- Default theme: light. Dark mode tokens exist; keep new styles theme-compatible (use semantic tokens, no literal white/black).

## Motion rules

- `lib/motion.ts` is the single source for everything JavaScript animates. Components NEVER hardcode a duration, easing, spring or delay — they call `useMotionPreset()`. CSS hover/focus transitions keep using the `--transition-fast` token (same 150ms).
- Durations: hover 150ms, fade 220ms, layout 320ms. Entrances use ease-out `[0.22, 1, 0.36, 1]`; layout changes and counting numbers use one spring (stiffness 220, damping 30, mass 1) — the same spring is sampled into a WAAPI `linear()` easing for `@number-flow/react`, so both run the same physics.
- Stagger is 40ms per item, capped at 6 items (240ms total). A list must stand complete within that.
- Entrances run ONCE. No re-animating on scroll, no looping decoration, no motion that has to finish before content is readable.
- Numbers animate their VALUE, not their opacity: a number that fades in reads as loading, a number that counts up reads as a result.
- `prefers-reduced-motion` collapses every duration to 0 — same variants, no time. Never gate content behind an animation.
- Three shared variants: `fadeRise` (entrance), `fadeIn` (entrance without travel, for elements whose position is their meaning) and `drawPath` (line drawing left to right).

## Quality bar

- TypeScript strict; no `any`, no `@ts-ignore` (use `@ts-expect-error` with a reason if unavoidable).
- Accessibility WCAG AA: semantic HTML, labels on inputs, focus-visible styles, 4.5:1 contrast for body text, color never the only signal. German `lang="de"` stays on `<html>`.
- Every interactive component handles loading, empty, and error states.
- Components small and typed; props interfaces exported. No default exports except Next.js route/layout files.
- All user-facing strings in German, formal product tone, informal address ("du").

## GDPR / health data (non-negotiable)

- No health data in localStorage/sessionStorage, URLs, query params, or console logs.
- No third-party requests at runtime (fonts, analytics, CDNs) without explicit instruction.
- Auth guard will protect `(app)` later; note it in comments where relevant, do not build auth unless asked.
- `/impressum` and `/datenschutz` stay as marked placeholders — never fill with invented legal text.

## Workflow

- Work in small steps; after each task run `npm run dev` mentally: the code must compile with zero TypeScript/ESLint errors.
- Conventional Commits (`feat:`, `fix:`, `chore:`…) if asked to commit.
- When something is ambiguous, choose the smallest reversible implementation and leave a `// ENTSCHEIDUNG:` comment explaining the choice.
